# Правила веток SkillArena

Эти правила действуют для разработчиков и AI-агентов. Цель — сохранять работающую связку frontend + backend и уменьшать конфликты при слиянии.

## 1. Назначение веток

| Ветка      | Назначение                                                | Что в ней хранится                                      |
| ---------- | --------------------------------------------------------- | ------------------------------------------------------- |
| `main`     | Проверенная версия для совместного запуска и демонстрации | Полный проект, общий API-контракт, тесты и документация |
| `frontend` | Разработка интерфейса                                     | Полный проект; основные изменения в frontend-файлах     |
| `backend`  | Разработка API и хранения данных                          | Полный проект; основные изменения в backend-файлах      |

Все три ветки содержат оба приложения. Не удаляйте «чужую» часть из своей ветки. После интеграции обе рабочие ветки получают изменения из `main`, включая исправления, сделанные при слиянии.

Обычный путь изменений — `frontend` или `backend` → Pull Request → `main`. Прямое исправление в `main` допустимо по явному поручению ответственного за интеграцию; после него обязательно обновить обе рабочие ветки.

## 2. Зоны ответственности

| Зона                                                                                             | Основной владелец                                        |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| `app/`, `components/`, `lib/domain.ts`, `lib/fixtures.ts`, `tests/domain.test.ts`                | Frontend                                                 |
| `backend/src/`, `backend/test/`, `backend/scripts/`, `backend/README.md`, `backend/Dockerfile`   | Backend                                                  |
| `backend/src/contracts.ts`, `backend/src/client.ts`, `backend/openapi.json`                      | Backend с обязательной проверкой совместимости frontend  |
| `lib/workspace-api.ts`, `lib/brief-api.ts`, `tests/integration/`, `docs/frontend-integration.md` | Общая интеграция                                         |
| `package.json`, `pnpm-lock.yaml`, `next.config.ts`, корневой `tsconfig.json`                     | Frontend; изменения общего запуска согласуются с backend |
| `backend/package.json`, `backend/package-lock.json`, `backend/tsconfig*.json`                    | Backend                                                  |
| `scripts/dev.mjs`, `.github/`, `.env.example`, `README.md`, `AGENTS.md`, этот документ           | Общая инфраструктура и правила                           |

В рамках одной задачи можно менять обе стороны, если это необходимо для совместимости. Такие изменения описываются в одном PR и проверяются вместе. Перед параллельной работой над общим файлом назначьте одного исполнителя; второй передаёт ему нужное изменение.

Не включайте в задачу массовое форматирование, переименование или перенос чужих файлов. Форматируйте только изменённые файлы.

## 3. Перед началом работы

1. Проверьте `git status`. Сохраните незакоммиченные изменения отдельным коммитом или осознанно в stash; не используйте `reset --hard` для очистки.
2. Получите удалённые изменения и обновите свою ветку. Пример для backend (для frontend замените `backend` на `frontend`):

   ```bash
   git fetch origin --prune
   git switch backend
   git merge --ff-only origin/backend
   git merge origin/main
   ```

   Если локальной ветки ещё нет, вместо `git switch backend` выполните `git switch --track origin/backend`.

3. Если `--ff-only` отказал, локальная и удалённая ветки разошлись. Изучите коммиты и объедините их обычным merge; не применяйте принудительный push. Если ветка открыта в другом worktree, обновляйте её в том worktree.
4. Прочитайте [интеграционный контракт](docs/frontend-integration.md) перед изменением сетевого взаимодействия. Зависимости устанавливайте через `pnpm install --frozen-lockfile` в корне и `npm ci --prefix backend`.

## 4. Изменение API

- Источник серверных типов и схем — `backend/src/contracts.ts`; браузерный клиент — `backend/src/client.ts`. Компоненты интерфейса используют адаптеры в `lib/`, а не собственные несовместимые копии API.
- Переименование поля, изменение маршрута, обязательности, статуса или формы ответа требует обновления схемы, реализации, клиента, frontend-адаптера, документации и интеграционного теста в одной поставке.
- Предпочитайте совместимые изменения: новое необязательное поле вместо удаления старого. Если меняется сохранённый формат, обеспечьте чтение существующей SQLite-базы или добавьте миграцию; не требуйте удаления пользовательской БД.
- `backend/openapi.json` генерируется командой `npm run export:openapi --prefix backend`. После изменения схем включайте обновлённый файл в тот же коммит; не редактируйте его вручную.
- Не создавайте второй источник истины в `localStorage`. Опубликованные карточки, черновики, предложения, решения и XP обслуживает backend.
- Сохраняйте версии карточек, проверку конфликтов, `requestId` при повторе создания и отдельное ручное подтверждение публикации. Сетевая ошибка не должна превращаться в скрытый успешный demo-ответ.
- Не меняйте без отдельного требования правила продукта: низкий рейтинг не запрещает отклик; бизнес выбирает команды вручную; XP начисляется за принятый этап однократно; AI не подтверждает сведения за человека.

## 5. Зависимости, настройки и локальные файлы

- Node.js — 24+, pnpm — версия из `packageManager` в корневом `package.json`.
- В корне используется pnpm и `pnpm-lock.yaml`; в `backend/` — npm и `package-lock.json`. При изменении зависимости обновляйте соответствующий lock-файл, не создавайте второй для той же папки.
- Секреты и локальные адреса хранятся в игнорируемых `.env`/`.env.local`; в `.env.example` — только безопасные примеры. Ключ AI находится только на backend.
- Не коммитьте `node_modules`, `.next`, `dist`, SQLite-файлы и логи. Не добавляйте изменения `next-env.d.ts`, вызванные только переключением Next.js между dev/build; этот файл генерируется инструментом.
- Общий запуск — `pnpm dev`. Изменения портов, proxy и env-переменных должны оставаться согласованными с `scripts/dev.mjs`, `next.config.ts`, `.env.example` и README.

## 6. Перед слиянием в main

На своей ветке сначала повторно получите изменения из `origin/main`, разрешите конфликты, затем выполните:

```bash
pnpm check
pnpm build:all
git diff --check
```

Если изменился API-контракт, дополнительно экспортируйте OpenAPI и проверьте его diff. Для изменения поведения нужны проверки соответствующего сценария; для правки только текста достаточно проверки документа и ссылок. В CI общий workflow запускается для `main`, `frontend`, `backend` и Pull Request.

В PR кратко укажите:

- что изменилось и как проверить результат;
- затронуты ли API, формат БД, переменные окружения или зависимости;
- какие проверки пройдены и какие ограничения остались.

При интеграционных изменениях проверьте путь «создать → подтвердить → опубликовать → откликнуться → выбрать → принять этап», сохранение после перезагрузки и ошибки API. В `main` не должны попадать неразрешённые конфликты или заведомо падающие проверки.

Для долгоживущих веток `frontend`/`backend` используйте обычный merge (или fast-forward, если доступен), сохраняющий исходные коммиты. Не делайте squash/rebase уже общей истории и не переносите те же коммиты через cherry-pick в несколько общих веток: это затрудняет последующую синхронизацию. Не выбирайте целиком `ours`/`theirs` для конфликтующего файла без проверки обеих сторон.

## 7. После слияния

Обновите обе рабочие ветки из нового `origin/main`. Выполняйте блок только с чистым рабочим деревом; если ветка занята другим worktree, используйте тот checkout:

```bash
git fetch origin --prune
git switch backend
git merge --ff-only origin/backend
git merge origin/main
git push origin backend

git switch frontend
git merge --ff-only origin/frontend
git merge origin/main
git push origin frontend
```

Если в рабочей ветке есть новые собственные коммиты, обычный merge их сохраняет. После разрешения конфликта повторите проверки перед push. Не заменяйте ветку принудительно содержимым `main`.

**Итоговое правило:** следующий цикл разработки начинается с общей проверенной основы, а изменения API и его потребителей попадают в интеграцию вместе.
